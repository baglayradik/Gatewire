# Участие в разработке Gatewire

Спасибо, что хотите улучшить Gatewire! Здесь описано, как настроить проект и что нужно для принятия pull request.

## Прежде чем начать

- **Ошибки:** создайте issue по шаблону «Сообщение об ошибке» с минимальным примером воспроизведения.
- **Новые возможности и изменения API:** сначала создайте запрос на новую возможность, чтобы обсудить решение до написания кода.
- **Уязвимости:** не создавайте публичный issue, следуйте инструкции в [SECURITY.md](SECURITY.md).

## Настройка окружения

Нужен Xcode 16 или новее (Swift 6.0+).

```bash
git clone https://github.com/baglayradik/Gatewire.git
cd Gatewire
open Package.swift
```

Сборка и тесты на macOS:

```bash
swift build -Xswiftc -warnings-as-errors
swift test -Xswiftc -warnings-as-errors
```

Тесты на iOS Simulator (подставьте симулятор, установленный у вас):

```bash
xcodebuild test -scheme Gatewire-Package -destination "platform=iOS Simulator,name=iPhone 16"
```

## Правила написания кода

- **Swift 6 language mode без предупреждений.** CI собирает пакет с `-warnings-as-errors`.
- **Безопасность concurrency.** Публичные типы реализуют `Sendable`, общее изменяемое состояние хранится в actor. Избегайте `@unchecked Sendable`, а если без него не обойтись, объясните причину в комментарии.
- **Явные existential-типы и импорты.** В пакете включены `ExistentialAny` и `InternalImportsByDefault`: пишите `any Protocol` и используйте `public import` только тогда, когда типы зависимости видны в публичном API.
- **Никакого кода под конкретный проект.** Всё, что нужно одному приложению или бэкенду, должно подключаться через публичный протокол.
- **Документация и комментарии на русском.** У каждого публичного объявления есть документирующий комментарий. Документирующие и обычные комментарии в коде пишутся на русском, идентификаторы — на английском.
- **Тесты.** Новое поведение покрыто тестами на Swift Testing. Тесты никогда не обращаются к реальной сети: запросы подменяются через `StubNetwork` из `GatewireTesting`.

## Pull request

1. Создайте ветку от `main`.
2. Держите изменение сфокусированным: посторонний рефакторинг оформляйте отдельным pull request.
3. Добавьте запись в раздел `[Unreleased]` файла [CHANGELOG.md](CHANGELOG.md).
4. Убедитесь, что CI зелёный, включая проверку ломающих изменений API.

### Ломающие изменения

Начиная с `1.0.0`, Gatewire строго следует семантическому версионированию. Ломающее изменение публичного API требует повышения major-версии. Прежде чем удалить API, пометьте его `@available(*, deprecated, renamed:)` и оставьте минимум на один minor-релиз.
